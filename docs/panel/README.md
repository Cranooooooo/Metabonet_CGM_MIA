# Research Monitoring Panel

一个**科研实验进程记录与审核面板**的通用模板。产出是一个自包含的单文件 HTML,
双击就能打开,不需要构建、不需要联网(除了一个字体链接)。

它要解决的问题:一个研究做到中途,进展散落在日志、脚本输出和聊天记录里。
带人的、评审的、以及你自己三个月后回来看的时候,都需要一页东西说清楚:
**每一步在干什么、为什么这么干、现在到哪了、得到了什么、下一步做什么。**

![一页八步](https://img.shields.io/badge/单文件-HTML-1F1E1C) ![图型](https://img.shields.io/badge/图型-10%20种-F5572F)

```bash
git clone git@github.com:Cranooooooo/Research_Monitoring_Panel.git
cd Research_Monitoring_Panel

# 图表规范来自 lieflat-charts,需要先装(render.py 会从这里读配色 token)

python3 build.py example_steps.py index.html
# 用浏览器打开 index.html
```

只需要 Python 3 标准库,没有第三方依赖。

## 结构规范(这是模板的核心约定)

一个面板 = **一个标题 + 一段问题陈述 + 一排横向标签页**。
点标签页,下面切换到对应内容。每个标签页固定六个部分,**缺一不可**:

| 部分 | 字段 | 要求 |
|---|---|---|
| **名称** | `name` | 一句话说清这一步在做什么。比如「把 14 个数据集整理成一个池子」,不要写「数据处理」 |
| **目的与阶段** | `purpose` | 为什么要有这一步,它在整条链上处在什么位置。要写清楚**不做会怎样** |
| **实施方案** | `plan` | 有序列表。写**怎么做**以及**为什么这么做**,尤其是那些容易做错的地方 |
| **目前进度** | `status` | `done` / `running` / `partial` / `blocked` / `todo`,渲染成右上角的徽章 |
| **结果图表** | `charts` | 一张图只承担一个结论。没有结果时留空,会自动显示「尚无结果」占位 |
| **结论** | `conclusions` | **编号列表**。每条是一个独立的、可被反驳的判断,不是对图的复述 |
| **下一步** | `next` | 具体到可执行。包括「如果失败了怎么办」 |

顶部还有一个可选的**术语表** `GLOSSARY`,折叠显示。见下面的写作要求。

## 内容文件长什么样

把 `example_steps.py` 复制一份改成你自己的。骨架:

```python
TITLE  = "论文标题 —— 一句话说清这个工作要解决什么"
KICKER = "实验进程记录与审核 · 更新于 2026-08-30"
SHORT_TITLE = "短名字"          # 浏览器标签页用,2 到 4 个词
LEAD   = "一段话讲清楚:问题是什么、我们怎么做、边界在哪。支持 **粗体** 和 `代码`。"

GLOSSARY = [
    ("术语", "用大白话解释它是什么。一句话,不要展开。"),
]

NL = "\n"       # 图表标签里的换行

STEPS = [
 dict(
  name="第 1 步 · 做什么",
  status="done",                    # done / running / partial / blocked / todo
  status_note=" · 补充说明",         # 可选,跟在徽章后面
  purpose="为什么要有这一步。",
  plan=["怎么做,以及为什么这么做", "第二条"],
  charts=[
    dict(type="chunkyBars", h=360,
         title="一句结论式的标题,不是「图 1」",
         sub="怎么读这张图 · 单位是什么 · 越高越好还是越低越好",
         src="数据来源 · 样本量 · 图型名",
         data=[["类目一", 0.55], ["类目二", 0.01]],
         opt=dict(fmt="f3", hero=1, foot="页脚小字,全大写")),
  ],
  conclusions=["第一条独立结论。", "第二条。"],
  next="下一步具体做什么;如果这一步失败了,改成做什么。"),
]
```

生成:

```bash
python3 build.py my_steps.py index.html
```

## 十种图型

图表规范来自 [lieflat-charts](https://github.com/larashero3-dotcom/lieflat-charts),
配色用它的 **Wire(编辑部红)** 预设:灰阶承载数据,荧光橙 `#F5572F` 作为**唯一的视线落点**。

> **硬规则:每张图只给一个元素上橙。** 第二处上橙就等于没有主角。
> 用 `hero=<索引>` 指定,选那个**真正是本图结论**的元素,不要选最大的那个。

**先看数据是什么形状,再选图型** —— 不要先想「这一页要几张图」再去凑:

| `type` | 数据形状 | 关键参数 |
|---|---|---|
| `chunkyBars` | 少类目排名比较(≤6),竖柱 | `hero` `ref` `refLabel` |
| `chunkyRows` | 同上但标签长,横条 | `hero` `labelW` `ref` |
| `pairedBars` | 每个类目两个系列(如前后、两种方法) | `hero` |
| `divergingBar` | 有正负,或相对某条基准线的偏离 | `hero` `zeroLabel` |
| `tallyRows` | 各项**独立**的 0–1 量表(不是构成占比) | `chance` `chanceLabel` |
| `tickDonut` | **100% 构成占比** | `hero` `center` `centerSub` |
| `dumbbell` | 类目级的**前后对比**,一线两点 | `hero` `leftLab` `rightLab` |
| `hairlineLine` | 有序序列 × 多个系列(趋势、扫描) | `hero` `x` `xlab` `ylab` |
| `plumbScatter` | 二维散点(≤20 点),用来做选型 | `vlines` `xlab` `ylab` |
| `tickGauge` | 单个 0–1 的比值,当作大数展示 | `centerSub` `note` |

通用参数:`fmt` 取 `f1` `f2` `f3` `f4` `int` `int1k` `deg` `pct`;
`h` 是画布高度(默认 360,画布宽固定 820,通栏渲染);`foot` 是页脚小字。

数据格式:多数图型是 `[[名称, 数值, 悬停说明], ...]`;
`pairedBars` / `dumbbell` 是 `[[名称, 值一, 值二, 说明], ...]`;
`hairlineLine` 是 `[{"name": 系列名, "v": [...]}, ...]` 配 `opt["x"]`;
`plumbScatter` 是 `[[名称, x, y, 说明, 是否高亮], ...]`;
`tickGauge` 直接给一个 0 到 1 的数。

## 写作要求(比代码更重要)

这套模板是给**人**看的,不是给同行看的。三条硬要求:

### 1. 每引入一个专业名词,当场用大白话解释一次

反例:

> 掩码比例单调提高潜在编码的时间结构。

这句话里有三个没解释的概念,而且「提高结构」不是正常说法。改成:

> 训练时随机遮住一部分输入让模型去补。遮得越多,**摘要**(模型把信号压缩成的一小串数字)
> 里前后帧的关联度就越高(0.205 → 0.252)。但这个提升在当前做法里用不上。

目标读者是**本科生**。凡是需要读者停下来想一秒的词,都要就地解释,
或者放进顶部的 `GLOSSARY`。

### 2. 不用缩写和行话

`AUC` 写成「可分性分数(0.5 = 完全分不开,1.0 = 完全分得开)」;
`MSE` 写成「误差」;`ckpt`、`val`、`frac` 这类简写一律写全。
变量名、文件名、命令行参数照原样写 —— 那是代码不是行文,但要在旁边说明它是什么。

### 3. 只放**正确的**结果

因为代码写错、配置写错而产生的中间数字,**一律不进面板**。
它们记在项目自己的问题清单里。理由很实际:面板是用来快速判断进展的,
混进作废的数字只会造成信息过载,而且下一个读的人分不出哪些数还算数。

同样的道理,**结论要写成可被反驳的判断,不是对图的复述**。
「A 比 B 高」不是结论;「A 比 B 高 2.5 倍,而且这个差距在 168 个人上组间抖动只有 0.005,
所以当初选 B 是个错误」才是。

### 4. 阴性结果照报,但要连同它的分辨能力一起报

如果某件事做不到,如实写做不到,并说明是**数据和物理的限制**还是**方法没做好**。
一个「没有显著差异」的结论,必须同时报出**这个测量手段能分辨多小的差异** ——
否则读者无法判断「没差异」是真的没差异,还是尺子不够精。

## 技术备注(踩过的坑,给下一个改这份代码的人)

1. **内联 JavaScript 时必须转义 `</script>`。**
   `mono-tokens.js` 的头部注释里就有一句 `<script src="..."></script>`,
   直接内联会让 HTML 解析器在那里提前结束脚本块,页面白屏,
   控制台只报一句含糊的 `MONO is not defined`。`render.py` 里的 `_inline_js()` 负责这件事。

2. **图表画布宽度写死会裁掉标签。** 参考实现是给半宽卡片设计的(400 宽);
   通栏渲染时行尾数值和散点标签会超出边界。现在所有几何都从 `viewBox` 推出。

3. **不要用 Chart.js / ECharts 的 CDN。** 如果面板要发布成在线制品,
   内容安全策略通常会拦截外部脚本。这里所有图型都是手写 SVG,
   把参考实现的**几何与数据编码**移植过来,不依赖任何外部库。

4. **改完之后跑一遍渲染测试。** 语法正确不等于跑得起来。
   最省事的办法是搭一个最小 DOM 桩,用 Node 把所有图实际渲染一遍,
   检查每张图画出的元素数量是否合理。
